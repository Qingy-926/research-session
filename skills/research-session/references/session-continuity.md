# Research project continuity

Current status belongs in the project README; protocols, numbers, and original evidence remain in their respective sources. Do not reconstruct a separate task list from full history or private memory. This reference defines reading and updating, not new services, hooks, models, or experiment authorization.

## Reading order

1. Read the top README continuity card: objective/stage, current task, next action, effective authorization and stop boundaries, latest ledger entry, and key evidence entry points. Aim for 15 lines/4 KiB; if longer, inspect for body material mixed in, but do not delete constraints to meet a size target.
2. Verify actual task rows, Git summary, process/exit evidence, and originals only where this task depends on them. A missing or stale card pauses only dependent execution; independent text-only work on supplied materials can continue.
3. Trace numbers to specified JSON fields and protocol. Only without a direct entry point locate the last 1–3 ledger entries, then inspect relevant detail if necessary. Old cards, review packs, and private memory are leads; they do not override current user decisions.

## When to write

- Roll forward the corresponding fields when the objective, authorization, task, state, or next action materially changes. Do not write a “checked this round” note for pure explanation without change. Update promptly when milestone or abnormal interruption requires continuity, not only at session end.
- Record conclusions, actual stage, observation time, and accessible evidence. Distinguish suggestion, preparation, running, exit, receipt, acceptance, and completion. Unregistered numbers cannot masquerade as authoritative conclusions; a card may provide verified values with source locations, without copying all results.
- Do not impose eight fixed fields. Fill continuity-relevant gaps in the project's existing format. Do not append a historical index every time; place genuinely historical material in its owning evidence file without overwriting originals.
- Before writing, check concurrent write ownership and SHA/targeted diff; change only this task's fields. If another session owns the file, provide a diff rather than taking over after timeout. A missing README does not block independent analysis or authorize a new project or restart of old work.

## Numbers, ledger, and versions

- Cite original artifacts for data, metrics, denominators, split/seed, selection, and verdicts; distinguish anomalies from valid negatives. Follow the project's current registration format; do not impose a new closed set to rewrite history.
- Record sources and supersession under project protocol for corrections. Do not rewrite frozen entries, raw results, or ledgers whose prefix must remain unchanged. Incorrect registrations and deletions also require authorization and recoverable evidence.
- Obtain current Git branch, file/process state, terminal status, and artifact existence from tools rather than memory. Check only where the task depends on them or writes; do not mechanically scan the entire repository for continuity.
- See [project work](project-work.md) for closeout and [independent review](independent-review.md) for the full review process. Record tool or permission gaps honestly; a commit, summary, or model opinion does not replace acceptance.
