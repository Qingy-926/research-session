## §6 独立模型异步复核（三个固定点）

开发者受控模式保留两轮和用户决定入口；自主推进、无人值守采用下述任务内连续整改，不要求新周期。自主推进/无人值守没有插件级固定轮数或固定请求次数；唯一硬约束是任务批准中的 `max_requests`、`reserved_requests`、`deadline`、`closeout_seconds` 与实质进展/安全停止，`6` 等次数只是具体批准值而非默认值，两轮规则仅适用于开发者受控模式。三个科研门、用户授权和原始证据不变。原 `--unattended-state` 控制器仍只用于离线合成夹具，不能将其三轮演练当成真实项目能力；真实会话的任务内复核走普通 dispatcher 的 `--task-approval`。

等待期间，请求方保持静默：不重复催问、不重复送审、不空转输出；可自主推进不依赖该复核门的已授权工作，但不得把未复核结果写成已通过。

旧双会话固定分工退役，当前主模型可按收益使用授权内子任务；下列三个科研独立复核点仍须完成，不由一般委派替代：

| 复核点 | 时机 | 必查项 |
|---|---|---|
| 1 批准前 | 预注册草稿完成后、执行前 | 判据出数前写死、门阈值依据、输入哈希门完整 |
| 2 出数后 | 正式判据出数、登记前 | 数字与 JSON 一致、未事后改判、辅助读数齐 |
| 3 汇报前 | 对外汇报文稿定稿前 | 数字四要素齐全、措辞边界遵守、不声称清单、fragile 宣称已按三选一处置（paper-audit.md 双门核查） |

流程（模板、JSON 合同和增量包见 [codex-review-pack.md](codex-review-pack.md)）：

1. **先固定审查对象与关闭条件**：协议是否自洽、实现是否符合协议、运行是否就绪分栏说明，不混成“整个项目无缺陷”。
   对实现主张，审前固定适用输入域、可信边界、正/负/边界验收用例及测试入口（按模板的 `acceptance_cases.json`）；
   科学/来源类主张固定所需原件、字段和核对方式，不伪造程序测试。固定条件不豁免真实新缺陷。
   主会话先完成可机械检查的验证，制作**自包含的最小证据包**到
   `01-资料/reviews/YYYYMMDD-HHMM__codex复核包__<主题>.md`；只包含本复核点所需原文、数字字段和证据片段，
   不堆叠历史意见，也不只给审计模型无法打开的路径。另建输入 JSON 清单，固定本对象跨版本不变的
   `review_id`，列全受控原件及影响结论的依赖 `files[{path,sha256}]`。
   复核包只能从项目权威 `01-资料/reviews` 送审；脚本按项目身份、`review_id` 和复核点维护用户级台账，
   移走回执、备份目录和整项目复制不能再开新的首审。发送前脚本在台账锁内重新核对历史并原子登记发送意图；
   同一项目身份、`review_id` 和复核点只允许一个进程进入发送，另一个直接停止，不留“先预检后登记”的窗口。
   历史项目用 `--ledger-backfill <项目根>` 只读回填，不修改任何旧回执或判词。
2. **先本地预检，再首次送审**：同一命令先加 `--dry-run`，检查绑定、包内保真度及当前合同模板，确认 active ID 与提交整改表一致。
   调用前按 [入口与只读核对](plugin-invocation.md#independent-review-entry-and-read-only-continuity-check) 设置 `RS_SKILL_ROOT`，始终使用本会话实际加载技能附带的脚本；同名共享副本与插件副本不能混用。
   新会话先从 README 定位当前原件/输入清单和历史回执，用 `review_preflight.py` 核实际脚本路径、规则摘要和精确兼容关系。该检查不发送、不碰台账、不继承旧通过；正式 `--dry-run` 仍是原送审准备流程，不冒充纯只读检查。
   `--show-contract --point <1|2|3>` 输出生产/消费共用字段与模板；`--validate-report <原报告或回执> --point ...`
   仅离线解析已收到的意见，支持追加 `--previous <基线>`，不访问代理、不产生放行。命令见模板。
   原文/源码片段只用 `review_evidence.py --source` 从文件生成，禁止手写后冒充原文；带路径、SHA和行范围并逐字节对账。
   测试摘要绑定机器可读 `verification.json`（命令、起止时间、exit、输入及日志SHA），不能只附旧日志路径。
   `--lint-pack` 可独立离线检查，正常送审也强制执行同一检查；细则和入口见 [review-evidence.md](review-evidence.md)。

   ```bash
   python "$RS_SKILL_ROOT/scripts/audit_dispatch.py" \
     --pack "<包绝对路径>" --point <1|2|3> --inputs "<输入清单绝对路径>"
   ```

   脚本只使用显式配置的 Responses 通道：通过 `--provider-config <JSON>` 或 `--responses-url <.../responses>` 与 `--model <模型>` 提供 URL 和模型，也可用对应 `RESEARCH_SESSION_*` 环境变量；两者缺一即返回 `provider_not_configured`，不获取发送锁、不发起请求。JSON 白名单为 `url/model/provider/api_key_env`，凭据值只从 `api_key_env` 命名的环境变量读取，不写入配置、绑定、回执或日志。仅限明确核实的端点，不自动切换通道；每次发送最多一次 HTTP 请求。请求名和响应模型字段不证明最终供应商或实际推理强度。把意见**追加到包尾**并生成同名 `.review.json` 证据回执（不改正文或科研原件）。三个复核点均须显式给出模型，并固定发送 `reasoning.effort=xhigh`；包尾记录的是请求值，不代表已核验上游实际采用的强度。上游拒绝该设置时复核未完成，不自动降档。
   **读 `review_completed` 与 `gate_passed`，不能只看送审是否返回。** `decision` 只用通过/待整改/不通过/未完成：
   exit `0` = 当前绑定版本通过，`3` = 待整改/不通过或轮次上限，`2` = 通道、材料、绑定或裁决合同未完成。
   未完成保留具体错误/缺证；不得视为通过，也不以重新送审替代诊断。
   格式不合格先用保存的原文离线定位/无损归一；不得把 `report=null` 直接作为复核基线再送整包。
   仅指定旧合同的首审 `test_case` 对象格式失败，可按模板显式恢复内存基线、离线核对原文与阻断 ID；
   原回执不变，原判词不变，恢复视图计作首轮且不是放行，不自动重发或扩权。
   The same explicit format-recovery flag supports the exactly bound first-round `reproduction.command` object-with-`argv` failure. It preserves the original object as `command_context`, validates the full original decision, and cannot restore a pass or a later round; no receipt is rewritten.
   新回执保存 `raw_report` 和 `review_counted`，格式失败不计实质轮次，也不新增重发预算；无法无损修复时报告缺少字段，必要时请求有界格式纠正，不重审内容。
   已登记规则哈希及准确错误匹配的首审 `repair.patch` 非空对象也可用同一显式入口恢复：重验原回执、包前后哈希及原文，补丁对象只无损序列化为字符串；仍须完整合同有效，拒绝通过和后续轮次。恢复视图仅作有效首轮计数，不写回原件、不授权发送。
   输出默认上限 32768，可用 `--max-output-tokens` 调整；上游仍可能有自己的限制。输出截断属响应未完成，不是科学否决；失败尝试另留诊断、不计实质轮次。默认不重发；显式指定
   `--retry-truncated-tokens <更高cap>` 才可在截断后重试一次，仍用原显式模型/xhigh，不降档；预检展示cap及既有HTTP重试上限。
3. **修复优先，不只转述整改意见**：实现阻断同次返回 `repair`：有足够源码时给可应用patch、绑定目标SHA和失败用例；
   否则明确缺哪段上下文、哪项用户取舍或为何不能安全修改，不能只说“请整改后重审”。纯证据/科学矛盾不强造补丁。
   当前独立脚本只收发文本，不赋予模型文件写权限。主会话核对目标版本、实际diff、授权及范围后，直接把可接受补丁应用到
   权威实现/测试并验证；有证据地否定则说明依据。不要求用户搬运意见、再说一次“修改”或为每文件求批。
   整改记录含问题ID、接受/质疑、原件实际改动、命令/结果/产物；改了什么与是否独立通过分开。
   审查不通过只暂停依赖硬门的步骤，不阻止这些已授权普通修复；项目已暂停或只准优化技能时不得借此恢复项目修改。
   科学协议、阈值、seed、数据、目标、预算、权限、共享配置及冻结证据不在补丁权限内，实质变更仍须用户裁决。
   复核方提出/编写补丁不等于已落盘，也不能自称独立验收通过；须由主会话实际回归，再按本次任务模式处理。
4. **分级处理**：`blocking` 必须定位当前阶段的真实缺陷及验收条件；`advice` 不阻断，
   `execution_gate` 留到其所属执行硬门。不能把当前硬门降为建议或推迟，也不能因未获 GPU/训练授权而否决只审设计的材料。
   实现阻断须给在声明输入域/真实调用链上可达的反例与可检验断言；仅有“可能还有漏洞”而无具体证据时列建议。
   论文缺证、泄漏或科学协议矛盾可以原件核对证明，不因写不成 pytest 自动降级。静态推演不能冒称已运行。
   复核方对阻断负责给最小反例/明确缺证及上述修复交付；计数/比例等定量断言附可复算定位，不能靠数错制造阻断。
   销项和时间线用 `verification_status` 明确本地/外部核实、未核实、未采集；状态不是通过开关。
   非必要历史过程记录缺失时收窄主张，不无限追问；泄漏、协议矛盾、缺原始证据等科学硬门不因此降级。
5. 需要复查阻断项时，主会话修改并本地验证后制作**增量包**：上一轮回执、逐项整改/未解决说明、
   实际 diff、验证结果及必要原始片段；沿用 `review_id`，更新输入 SHA，调用时加
   `--previous "<上一轮 .review.json>"`。第二轮只查旧问题、变化和受影响依赖；新增阻断需具体新证据，不能无依据扩张范围。 规则摘要不同时，仅已核实的兼容版本组合可接续；预检和新回执记录版本迁移，不修改旧回执或继承放行。未知变化仍须核查，详见 `review-rules-compatibility.json`。
   原验收条件已由绑定证据满足就关闭该项；发现新反例须写清它违反哪项原主张，追加独立用例或明确修正验收，
   不以更换措辞无限延长同一问题。历史已关闭ID另作注记，不混入当前必销项；未知ID不能替代当前ID。
   有证据质疑计数或事实时，在第二轮输入 `disputes` 给具体ID、绑定产物及复算命令/JSON pointer；复核方同轮逐项回应。
   校验器不执行包中命令；纠正某个计数不自动消除同项其他真实缺证，不为争议自动增加轮次。
6. **按任务模式控制后续审查**。自主/无人值守沿原ID和累计轮次，在批准范围、实质进展和预算内持续增量复核，不要求新周期。开发者受控模式一次主审、一次整改；仍有阻断/争议则写回README并由用户裁决，后续才使用「用户决定的新周期」。任何模式都不换名清零、不自动通过、不反复全文互审。
   台账显示回执已移出权威目录、存在未闭合发送意图、来源不明的历史锁或无法解析的复核记录时，先人工核对，不自动重发；
   损坏的复核回执/尝试/锁记为 `unreadable`，项目级阻断。无法访问的目录可能包含更深层的复核记录，
   因此任何扫描访问失败均使 `complete` 和 `review_complete` 为 false，并阻断新送审。
   扫描使用 Windows 长路径前缀；长路径不再因 MAX_PATH 被误判为访问失败。目录 junction 单独记入
   `link_exclusions`：内部链接由真实目标覆盖，外部链接目标含 `reviews` 仍阻断，断链无法承载记录且不阻断；
   其余访问失败和损坏记录仍按严格口径阻断。
   损坏文件在原路径修复后须完整重新回填；成功解析的记录和解除记录追加到台账，原有记录保留。
   文件消失不能证明已恢复，应先找回并核对，不能直接清除阻断。
   确认上游未送出后用 `--resolve-ledger <entry_id> --ledger-note <核查依据>` 解除该意图，再按当前任务模式和预算处理。
   对旧版已送出的意图，人工核对其对应回执后用 `--resolve-ledger <entry_id> --ledger-note <核查依据> --ledger-receipt <回执路径>`；
   回执须已登记且与该意图的对象、复核点、周期和包摘要一致，记录其 SHA256；同摘要不自动证明对应关系。
   该解除只消除“发送状态未知”的阻塞，不等于新一轮复核，也不新增执行、登记或定稿授权。
   自主/无人值守有效非通过回执返回 `task_revise`，不论第几轮；能否再送取决于批准、实际整改证据和剩余额度。受控模式仍用 `revise_once/rejected_stop/needs_user_decision`。无法补齐、没有进展或约定验证不支持主张时如实交付，允许停止/放弃主张/缩小范围；后两者若改变任务目标仍须用户决定。`report=null`、合同失败和传输失败先诊断，不以持续整改入口重试未知响应。
7. **复用绑定，而非复用口头结论**：同对象、复核点、原件/依赖、包正文和规则不变时直接复用回执，不再次请求模型；
   任一绑定变化就不能继承旧通过。旧包/意见/回执留作沿革，README 仍是唯一当前交接入口。
8. 结论始终是审查意见，不是实证，不新增执行、登记或定稿授权；已获相应授权时也不重复求批。
   项目硬门和 autonomy-bounds.md 的边界不变。

### 已核实的测试夹具误登记（仅台账维护）

已独立核查的具体非权威回执，既无正式 schema、pack、intent_id、模型及包摘要绑定时，按原流程逐条认定。
含正式字段的原生合成消费夹具只能使用下述额外来源证明；正式字段不自动否决来源，也不自动证明可排除。
目录名、缺字段、同名源码、哈希或非空说明都不能证明来源；不自动跳过 tests 或备份。
维护操作者先从台账原条目生成未裁决草稿，独立审核者核对具体测试源码、输入、完整生成字节及留存运行记录，
在实际审核原件中给出逐条结论、依据、未核实项和限制；由宿主任务/对话证据核实审核者和操作者职责分离。
不能自填两个名字后冒称独立审核。主会话据审核原件填入草稿，绑定审核原件 `review_record{path,sha256}`
及全部相关 `evidence[{path,sha256}]`，不得把原回执或草稿本身当作审核原件。
路径使用绝对路径；审核原件、证据、夹具及它们的父路径不能是重解析点/符号链接，末端不能有硬链接。
权威 reviews 及其子目录中的回执永不允许按夹具排除。

原生消费夹具须在同一审核记录增加 `native_provenance{path,sha256}`，并将其列入 `evidence`。
其 JSON schema 为 `research-session/native-fixture-provenance/v1`：
`producer` 绑定留存生成源码；可选 `producer_input_path` 指出运行记录中的原源码绝对路径；
`verification` 绑定留存的 `research-session/verification/v1` 成功记录及日志。
该运行输入须同时记录生成源码的前后 SHA 与留存源码一致。
`rows` 中每条含精确 `entry_id`、完整原台账 `target`、
`artifacts[{original:{path,sha256},preserved:{path,sha256}}]`，逐件核普通无链接属性及两副本SHA一致，
至少包含回执和其包。全部路径绝对、证据持续可读；不执行生成源码或包中命令。
当前此入口只接受独立核实的本地消费形态：模型为fixture，intent/guard为fixture-intent/fixture-guard，
route仅含wire_model=fixture。上述形态只是额外拒绝门，不能替代独立审核真实生成过程与留存运行证据。
项目内存在匹配intent、guard或同对象/点/包摘要的send_intent、attempt或lock时拒绝；
纠正后发现此类记录或任一来源证据失效也恢复阻断。请求、费用、未知发送、轮次及旧条目均不删除或重置。
重复应用不重复追加，重新扫描沿用原条目并重核证明；并发应用在台账锁内串行，撤销仍按原追加入口。
信任边界仍是台账维护者与实际独立来源审核；哈希、fixture字符串和用户批准均不认证来源。

```bash
python "<已安装技能>/scripts/audit_dispatch.py" --fixture-template "<原 entry_id>"
python "<已安装技能>/scripts/audit_dispatch.py" --resolve-fixture "<原 entry_id>" \
  --fixture-attestation "<审核记录绝对路径>" --fixture-sha256 "<已核对 SHA256>" --dry-run
python "<已安装技能>/scripts/audit_dispatch.py" --resolve-fixture "<原 entry_id>" \
  --fixture-attestation "<相同记录>" --fixture-sha256 "<相同 SHA256>" --confirm-independent-review
python "<已安装技能>/scripts/audit_dispatch.py" --revoke-fixture "<原 entry_id>" --ledger-note "<撤销依据>"
```

模板输出到标准输出，由当前文件工具建立审核记录；模板 `decision=null`，不是判断或授权。
先预检，再由操作者明确确认已核实独立原件；确认参数仅留痕声明，不是身份认证。
纠错/撤销与送审参数互斥，不发送请求、不更改旧回执、原判词、复核次数和科学执行授权。
台账原条目和纠错历史只追加保留；变更证明必须先撤销再审核。原条目、证明、审核原件或任一证据失效时恢复阻断。
可信边界是维护操作者、台账写权限及真实独立审核流程；哈希只能核字节，不证明来源、身份或防篡改。
扫描前至请求发出期间须停止项目相关文件的外部写入，维护期间不得混用旧客户端；台账锁不能锁住整个文件系统。
预检/认领刷新所有已登记同身份项目根，未登记的外部副本不保证被发现；已知副本须先回填。旧客户端不识别纠错，继续保守阻断。
发送进程崩溃不自动清除发送意图或发送锁。Windows 台账互斥由进程持有的独占文件句柄管理，进程退出后由内核释放；
旧版台账哨兵先以共享只读方式检查，确认旧 owner 已退出或 PID 复用后，再独占重读并处理该实例，不干扰存活旧客户端。
发送锁与台账互斥的恢复含义不同；未知发送按下节核查，不得为解锁改写/截短台账或直接删发送锁。

### 已终止发送的受控恢复（仅本地维护）

发送可能处于仍在运行、结果未知、确认失败但无有效回执、已有有效回执但清理中断等状态。进程退出、等待超时、
不存在回执、模型名称无效或操作者说明，单独均不能证明可以重发。先停止该对象的外部写入及旧客户端使用，
回填所有已知同身份项目副本，再通过本会话实际加载的正式入口生成绑定草稿：

```bash
python "$RS_SKILL_ROOT/scripts/audit_dispatch.py" --recovery-template "<锁 entry_id>"
python "$RS_SKILL_ROOT/scripts/audit_dispatch.py" --recover-send-lock "<相同 entry_id>" \
  --recovery-evidence "<核查记录绝对路径>" --recovery-sha256 "<已核 SHA256>" --dry-run
python "$RS_SKILL_ROOT/scripts/audit_dispatch.py" --recover-send-lock "<相同 entry_id>" \
  --recovery-evidence "<相同记录>" --recovery-sha256 "<相同 SHA256>" --confirm-recovery-review
python "$RS_SKILL_ROOT/scripts/audit_dispatch.py" --revoke-send-recovery "<recovery_id>" --ledger-note "<撤销依据>"
```

草稿的 `decision/outcome` 为空；模板和 dry-run 不改变台账或清锁。实际恢复与送审、换周期等参数互斥，不访问模型。
仅在以下证据全部满足后，操作者才确认应用：

- 所有已登记根都可完整读取，没有无法解释的复核记录；原进程确已退出或 PID 已复用，无法核实或仍存活即停止。
- 精确绑定项目、对象、复核点、周期、包摘要、锁实例（摘要与时间）、对应 intent 和所有尝试；存在后续 intent、
  其他对象锁或绑定变化时重新核查。现代 guard 在认领前崩溃仍须绑定该 guard；缺少 intent 与实例身份的旧锁不猜测归属。
- 确认失败且无有效回执时，选择 `decision=recover_failed_send`，`outcome=not_accepted` 或
  `terminated_without_valid_review`。结构化 4xx 拒绝（不含 408/409/499）且有上游错误 code，可作为该调用的拒绝证据，
  不限于 `model_not_found`。超时、5xx、截断、缺失本地 attempt 等状态，须取得逐请求 gateway/upstream 终态原件，
  证明 rejected/failed/cancelled 且无有效审查；不能据本地进程死亡推断远端终止。
- 不确定请求逐一填 `upstream_confirmations`（单请求也可用 `upstream_confirmation`）：绑定 intent/guard、
  已知 response_id、终态、核查时间和原件 `record{path,sha256}`；多个不确定请求还须逐个绑定 attempt SHA，
  不能用一个请求的证明解除另一请求。无法取得终态证据时保持阻断并说明具体缺件，不自动重试。
- 明确尚未发送的认领前崩溃另有本地证据入口：仅现代 guard、完整历史无对应 intent/attempt/receipt 时，
  可填 `source_kind=local_pre_request,terminal_state=not_sent`，绑定 guard、独立核实的运行轨迹 `record`、
  核查时间及 `implementation[{role,path,sha256}]`。两份留存源码 role 必须是 dispatcher/ledger，其 SHA 须与 guard
  创建时留存的一致；独立审核还须核实该实现确在持久认领后才调用网络，以及轨迹确未越过该边界。
  缺少这些证据不能仅据“没有 intent”推断未发送；已有 intent 或任何尝试不能走此入口。后续软件升级不替换已绑定源码快照。
- 已有对应有效回执时，选择 `decision=reconcile_receipted_send,outcome=receipt_preserved`。重验完整回执合同及包前后摘要、
  intent/guard/周期，保留原回执、判词和次数；不能用旧同对象回执关闭新锁，不能把回执损坏归为失败后重发。
- 实际独立审核者核对原件、逐请求终态、归属与限制，在单独审核原件留结论。操作者绑定
  `review_record{path,sha256}`，如实填 operator/reviewer、reviewed_at、basis 和 limitations，并由宿主证据核职责分离；
  两个名字或确认参数不认证身份，不得自填冒充独立审核。证据原件及父路径不得为重解析点，末端不得有硬链接。

应用先追加 `send_lock_prepared`，归档精确锁与当前包快照，再解除该实例并追加 `send_lock_recovered`；
历史 intent/attempt/receipt/判词不改。恢复中断后沿用相同证据重入，完整重核历史；不因物理锁消失就认定完成。
正常 owner 清理已经被竞争者登记的 guard 时，也先持久归档并追加精确实例的 `send_guard_release_prepared`，
再删锁和追加 `send_guard_released`。准备记录仅在旧实例已消失且归档仍有效时闭合旧记录，物理旧锁仍在不能提前放过；
同路径的新实例仍独立阻断。这使删后落账前崩溃可解释，不依赖操作者猜测或另发请求。
撤销只追加记录，不重建物理锁；审核原件、终态证据、归档或绑定失效时重新阻断。
维护信任边界仍是台账写权限、操作者和真实独立核查；摘要只能核字节，不能证明来源或远端事实。
恢复不新增次数、发送预算、新周期或科研执行授权，也不自动发起下一次审查；后续仍须原流程的全部门。

### 首审报告的受控格式纠正

已保存且绑定包尾的首审报告若仍有覆盖状态/问题关联矛盾，不能由请求方改判，也不能重新送整包。
在明确的格式维护和请求预算授权内，使用[格式纠正命令](codex-review-pack.md#受控格式纠正旁证)。
仅原路径的正式round0/report=null/review_counted=false合同失败可用；精确兼容规则、原模型/
provider/credential route和xhigh不变。单HTTP；原发送身份在共享台账目录原子认领，原件副本、
并发、移走本地marker均不能增加请求，未知/失败/不合格纠正保持停止，无自动重试。

纠正只允许coverage的status/finding_ids变化及保留完整上下文的locator数组归一；
原判词、问题、证据、修复、定量值及类型、理由和缺证逐项不变。收到有效终态也先保存原返回再解析。
原回执、原包与历史轮次不改；旁证gate_passed/review_completed/review_counted均false。
后续显式--corrected-previous重新核原件、请求、共享认领、原始返回和旁证并绑定全部摘要；
仅恢复内存中effective round1的非通过基线，普通整改最多到round2，不继承放行或新增权限。
可信边界仍是维护者与台账/证据写权限；摘要不认证reviewer身份或上游来源。

### 任务内连续整改

适用于已由宿主核实用户来源的自主推进、无人值守任务批准。AI从现有任务书和对话整理一次绑定，不要求用户重复批准或手填JSON。沿用 `review_id`、point、cycle和完整旧判词，round逐次累计；可接续精确兼容的6.0.1终态，不派生 `__cN`。原计划若明确禁止后续调用或预算已过期，须遵守该限制；新版不能追溯扩大旧授权。

```bash
python "$RS_SKILL_ROOT/scripts/audit_dispatch.py" \
  --pack "<增量包>" --point 1 --inputs "<当前原件清单>" \
  --previous "<上一有效回执>" --task-approval "<任务批准绑定.json>" --timeout 1200
```

首次送审也带 `--task-approval`（省略 `--previous`）。先以 `--dry-run` 预检。批准记录、批准来源和所有进展验证及日志须纳入当前 `files`。任务记录schema为 `research-session/review-task/v1`：

```json
{
  "schema": "research-session/review-task/v1",
  "task_id": "approved-task",
  "mode": "autonomous",
  "project_id": "category/project-123",
  "review_ids": ["stable-object-id"],
  "points": [1, 2],
  "approval_source": {"path": "<absolute user decision record>", "sha256": "<full SHA256>"},
  "started_at": "<absolute timestamp with timezone>",
  "deadline": "<absolute timestamp with timezone>",
  "closeout_seconds": 1800,
  "max_requests": 12,
  "reserved_requests": 2,
  "revoked": false
}
```

`mode`也可为`unattended`；无金额上限可沿任务书不设金额。`max_requests`是本任务分配的总请求额度；台账锁内累计项目自started_at后的全部dispatcher发送，按意图、失败尝试和最终回执核实际次数，包含旧版显式截断重试，跨对象/点共用。相关意图仍有未知发送时停止。格式纠正、委派等其它通道须由宿主事先计入`reserved_requests`并核总体计量；不得掩盖未知费用或超出已批准预算。不得改task_id、起点、时限或额度重置计数。单次timeout加收尾必须容纳在剩余时间内。

增量清单还须含`remediation_progress:[{finding_id,path,verification}]`：定位上一有效回执的当前blocking ID、实际改变的受控原件或新增证据，以及本轮`verifications`中的成功机器记录。验证须在上一回执后实际执行，绑定改动原件、日志及前后SHA；换包名、改批准或只生成日志不算进展。宿主仍须核实改动与阻断的语义关系，摘要和JSON不证明用户身份、验证独立性或实质进展。无新进展停止重复送审。

发送锁、未知发送、原合同和科学硬门照旧。此入口不发起循环、不自动重试、不授予研究执行或后台运行能力；每次调用只发一次HTTP。计量/时限失效、批准撤回、范围/协议变化或用户暂停即停相关分支。回执的`task_revise`仅表示未通过后的整改出口，仍须逐次检查这些条件。

### 用户决定的新周期（仅开发者受控模式）

本节仅适用于开发者受控模式，自主/无人值守使用上一节。两轮按同一 `review_id` 计数，不因换包名、换对象 ID 或重开主审而重置。触发点是两轮结束（`needs_user_decision`）或首轮明确否决（`rejected_stop`）；首轮待整改先走整改复核；首轮未完成/响应截断先诊断补证。只有用户明确决定再开一个周期时，才按本节执行，不把普通“继续修改”自动解释为该决定。

脚本核对：上一周期必须已两轮结束或首轮明确否决；新 `review_id` 必须是根 ID + `__cN`，非新周期的 `review_id` 不得以 `__cN` 结尾（不区分大小写、忽略首尾空白）；新周期包须与上一周期回执放在同一 reviews 目录；新周期与上一周期至少共享一个非回执受控原件；决定记录和上一周期最终回执必须列入 `--inputs` 的 `files`；决定记录须含上一周期 `review_id`、上周期回执 SHA256 和新 `review_id` 的字面值（各占一行）。脚本不认证用户身份，只核对这次过渡是否可追溯；决定本身仍由用户作出。

```bash
python "$RS_SKILL_ROOT/scripts/audit_dispatch.py" \
  --pack "<新周期包>" --point <1|2|3> --inputs "<含决定记录与上周期回执的清单>" \
  --previous "<上周期最终回执>" --new-cycle "<决定记录>"
```

1. **先记录用户决定**：新周期首次送审前，在 `01-资料/reviews/` 建立
   `YYYYMMDD-HHMM__用户决定新周期__<主题>.md`，至少写明：用户原话（逐字引用，不得代写或概括）与决定时间；
   对象与复核点；上一周期 `review_id`、最终回执路径及 SHA256；上一周期轮次、结论和未解决项；
   为什么需要新周期（范围、方案或证据发生了什么变化）；新周期 `review_id` 与本次不审范围。
   用户原话须逐字引自宿主对话，伪造即违规。同一决定同步写入项目 README；README 仍是当前交接入口。
2. **区分“新周期”与“新对象”**：研究结论、协议或对照对象实质改变时，是新审查对象，应新建 `review_id`，
   不套用本入口；对象和复核点不变、只是用户决定再给一个复核周期时，才用派生 `review_id`
   （根 ID + `__cN`，如 `<旧review_id>__c2`；根 ID 是去掉已有 `__cN` 后缀的部分）。
3. **绑定旧证据**：新周期的 `--inputs` 清单除常规原件外，必须把决定记录和上一周期最终回执列入 `files`，
   由脚本校验 SHA。新周期因此是可追溯到用户决定和旧证据的显式延续，不是换名重开。模型看不到清单文件，
   新包背景须引用用户决定原话，并列出上一周期未解决项摘要。
4. **送审与上限**：用派生 `review_id` 新建复核包，带 `--previous` 和 `--new-cycle` 送审；脚本记录周期号，
   轮次从第 1 轮开始，仍受同一对象两轮上限约束。旧回执、旧包和旧判词只读保留，不改写、不迁移、
   不充当新周期审查基线。
5. **不继承、不放行**：新周期不继承旧周期的“通过”或待整改结论。旧阻断项仍须在新包中逐项说明：
   已关闭的给证据，未解决的保留；若因范围变化不再适用，写明原因而非静默删除。决定记录和新包须列全
   上一周期 `blocking` ID 及状态（新周期虽带 `--previous` 作证据，但不以它为审查基线，没有
   `closed_findings` 自动销项）。新周期结论仍是审查意见，不新增执行、登记或定稿授权。
6. **一次决定一个周期**：每个新周期都要有独立的用户决定记录；不得预先批量派生 `__c3`、`__c4`，
   也不得在无新决定时连续派生。用户不再明确决定时，坚持原两轮上限并交付分歧。

### 复核全面性与不得无据扩张

**隔离候选首审（显式 `first_review`，不适用于已安装版本）**：

1. 主会话列出材料实际作出的关键主张，逐条编号，并提供结论位置及对应原件；固定必查项不会被这份清单替代。
2. 复核方先核完固定项和关键主张，再从结论反查原件的字段、版本、口径与分母。发现错误后横查同一根因涉及的正文、表图和摘要；同根因合并一项但列全位置。遇到缺证只冻结对应判断，其余继续查完。
3. 每条核对记录标明依据/缺证并关联问题。阻断项写清**位置、实际与预期、影响、最小改法、验收**。代码原文够就给最小补丁与用例，文字给替换句；无法确定时点明缺哪份原件、字段或决定。
4. 首审有必要缺证则为「未完成」且列出已证实的问题，先定向补证，不自动重送；已有充分证据否决主张则「不通过」。无阻断才「已通过」。待整改逐项标明是可本地验收，还是需独立判断，并写明后者具体判断什么。

本地验收候选只限复核点 3 已绑定的 Markdown/文本展示更正。所有阻断均满足该条件、原证据
及结论不变时，主会话可按首审的精确替换逐项整改，再离线验证；不能变更数据、口径、协议、
科学结论或授权。候选输出 `locally_verified`，不写回回执、不等同正式科研门放行。
有混合项时，先做并验证本地更正，第二轮仍逐项交代旧阻断，只对尚需判断和受影响依赖审理，不重审全文。
候选输入及命令见 [模板的候选合同](codex-review-pack.md#候选首审合同)；未选择候选时沿用原流程。

- 首轮必须一次性给出当前阶段所有可证实的阻断项，并在 `location/change/acceptance` 写清“改哪里、改成什么、如何验收”；不得只给方向性意见让主会话猜。
- 不得用风格、措辞、可读性、可选优化或“可能还有漏洞”制造阻断；这些只能记 `advice`。`blocking` 只留给会影响当前阶段有效性、且能用原件、调用链或最小反例证明的缺陷。
- 整改复核只审旧阻断、实际 diff 及受影响依赖。与本次修改无关的新问题不得新增为 `blocking`，只能记 `advice` 或留待用户决定的新周期；只有新证据表明旧结论失效时才可新增阻断，并须说明它违反了哪条原主张。数据泄漏、协议矛盾、缺原始证据等科学硬门不在此限，仍按原件核查阻断。
- 同一问题不得换措辞重复阻断，也不得以每轮抛出一个新阻断的方式无限延长。首轮列全、后续收敛，是复核方的交付责任。
